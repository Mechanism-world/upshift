# ADAPT_EDITS — human-edit ledger for the policybench adapter

`upshift adapt` was **not** run for this case. The target ships the exact request its harness
sends behind a single pure function, so the adapter was generated by executing that function
against the repo's own pinned scenario manifest, inside the lab container
(`cases/a-032/home/gen/gen_requests.py`, output `home/gen/requests.json`). That is strictly
more faithful than a model extraction over cited evidence, and it cost $0.

Source of the wire shape: `policybench/eval_no_tools.py::_chat_completion_request_kwargs`
(lines 691-741 at `ad1583fe`) for the OpenAI-flavoured kwargs, and
`policybench/batch_eval.py::_openai_kwargs_to_anthropic_params` (lines 180-226) for the
harness's own translation of those kwargs into Messages-API params.

## File by file

### `tools.json`
Verbatim `_build_answer_tool(["free_school_meals_eligible"], country="us",
include_explanations=True)` — the same object for all seven cases (verified: one distinct
schema across the seven generated requests). No edit.

### `system_prompt.txt`
Empty, 0 bytes. policybench sends `messages=[{"role":"user", ...}]` and no system message;
upshift omits an empty system block entirely (`src/upshift/agent_loop.py:170-174`), so the
wire matches. **This is not a gap in the extraction — the agent has no system prompt.**

### `agent.json`
| field | value | source |
|---|---|---|
| `endpoint` | `messages` | `batch_eval.py:180-226` translates the harness's kwargs to the Messages API |
| `model` | `claude-fable-5` | `policybench/config.py:37` |
| `params.max_tokens` | `16384` | `_completion_controls("claude-fable-5", …)` → `max_completion_tokens=16384` (`eval_no_tools.py:586-597`, `THINKING_CLAUDE_MAX_COMPLETION_TOKENS_CAP`), mapped to `max_tokens` by `batch_eval.py:187` |
| `params.tool_choice` | `{"type":"tool","name":"submit_outputs"}` | `eval_no_tools.py:727-741` forces `{"type":"function","function":{"name":"submit_outputs"}}`; `batch_eval.py:206-211` translates that to `{"type":"tool","name":…}` |
| `max_turns` | `1` | policybench is single-shot: it reads the first response's tool-call arguments and stops. Anything above 1 would let upshift's loop return the tool result and, under a forced `tool_choice`, elicit a second forced call that the harness never sends. |

Deliberately **not** carried over: `caching` (a litellm response-cache flag, not a wire
parameter) and `timeout` (`300`, a client-side deadline). No temperature, top_p, top_k,
`thinking` or effort parameter is sent by the harness for this model
(`REASONING_EFFORT_OVERRIDES` is empty, `eval_no_tools.py:163`), and none is sent here.

### `backend.py`
Written by hand. policybench's `submit_outputs` is a terminal answer contract, not an action,
so the backend only records the submitted values. In-memory, deterministic, never raises.

### `cases/cases.json`
Seven cases, one per household, all asking for the single output
`free_school_meals_eligible`.

- **Unit.** One (scenario, output) pair per case, because `claude-fable-5` is in
  `GRANDFATHERED_CHUNKED_CLAUDE_MODELS` (`eval_no_tools.py:178-186`) and therefore gets
  `CLAUDE_EXPLANATION_CHUNK_SIZE = 1`: the harness really does send one output per request
  for this model.
- **Why one output for all seven cases.** `_build_answer_tool` embeds the requested variable
  names in the tool schema, so a multi-variable suite would need either a per-case schema
  (which upshift's one-`tools.json` contract does not allow) or a hand-written union schema
  that the target never sends. Holding the output fixed keeps `tools.json` byte-exact.
- **Which output.** `free_school_meals_eligible` is the highest-`exact`-rate output for
  `claude-fable-5` in the repo's own committed snapshot run
  (`paper/snapshot/20260501/runs/us_full_run_20260612_policyengine_4_16_1_populace/analysis/metrics.csv`:
  `exact = 0.99`, `n = 100`, `coverage = 1.0`) that also has a non-degenerate mix of reference
  values (8 of 100 households eligible). Outputs with `exact = 1.00` were rejected:
  `local_income_tax` is 0.0 in all 100 households, and
  `reduced_price_school_meals_eligible` has a single non-zero household, so a suite built on
  either would be passed by a constant responder.
- **Which households.** The four lowest-numbered households whose reference value is 1
  (`scenario_008`, `_012`, `_032`, `_038`) and the three lowest-numbered whose reference
  value is 0 (`scenario_000`, `_001`, `_002`). A constant responder scores at most 4/7.
- **Expected values.** `paper/snapshot/20260501/us_reference_outputs.csv`, the repo's own
  committed PolicyEngine 4.16.1 reference outputs. No expected value was invented, and none
  came from a model's answer.
- **Checks.** Deterministic only: `no_api_error`; `tool_called submit_outputs`
  `min_times = max_times = 1` (the prompt itself says "Use the `submit_outputs` function
  exactly once"); `final_state dollars.free_school_meals_eligible == <reference>`. No LLM
  judge.

## Known deviations from the target, stated up front

1. **Grading tolerance.** policybench scores an answer correct within $1 of the reference.
   upshift v0.3.1 has no numeric-tolerance check, so the backend rounds the submitted value
   to the nearest whole unit and the case asserts equality. For the 1/0 eligibility output
   this suite uses, the two rules are identical; the deviation would only matter for a
   currency output.
2. **Prompt caching.** upshift always puts a `cache_control` breakpoint on the system block
   and the last tool definition (LAB_RUNBOOK §2.1). policybench does not. This changes price,
   not the model's inputs.
3. **Scope.** One of policybench's 18 outputs and 7 of its 100 households. The suite is
   evidence about this agent's request shape and this output, not about the leaderboard.
