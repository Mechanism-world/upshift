## `backend.py` — full rewrite

adapt's generic engine classified the three tools correctly (`lookup`, `lookup`, `update`) over
`state_key` `customers`/`orders`, which is the right *shape*. Three things made it unusable:

1. **State shape.** Its `_entries` helper flattens a dict bucket to `list(bucket.values())` and
   writes the list back into the state, so `state()` would no longer be keyed by order id and
   `state_count {path: "orders", where: {...}}` / `final_state {path: "orders.O1.status"}` could
   not address anything.
2. **Aliasing.** Upstream's `customers[...]["orders"]` entries are the *same dict objects* as
   `orders[...]` (cell 9), so a cancellation is visible through `get_customer_info`. adapt's
   version deep-copies both independently, so the customer view would go stale — a silent
   wrong answer, the worst failure mode for a fixture.
3. **Return shapes.** `_lookup` returns `{"results": [...]}` and `_update` returns the mutated
   entry; upstream returns the customer dict, the order dict, or a bare `True`/`False`, and its
   "Customer not found" / "Order not found" strings for a miss.

The rewrite implements cell 12 line for line, rebuilds each customer's order list from the live
`orders` dict on every read and in `state()`, and wraps every reply as
`{"result": <upstream return value>}`.

## `cases/cases.json` — 6 final cases

adapt found the right three requests (it had read the rendered notebook in `llms-ctx-full.txt`)
but drafted them with copied-prose checks and single-call oracle plans.

| adapt case | disposition |
| --- | --- |
| `customer-c1-email` | **kept** as `customer_c1_email`; `args_subset` → `exact_args`, added `turns_at_most 2` and a `state_count` guard that nothing was cancelled |
| `cancel-all-orders-c1` | **kept** as `cancel_all_orders_c1`; dropped the brittle `response_contains: "cancelled both orders O1 and O2"` (dictating phrasing is eval overfitting — CLAUDE.md, 2026-08-28), added `state_count {orders, status: Cancelled} == 2`, `max_times: 2` on `cancel_order`, `final_state orders.O3.status == "Shipped"`, `turns_at_most 3`, and an oracle plan that **batches** the two cancellations in one step |
| `order-o2-status-after-cancel` | **rewritten** as `cancel_then_check_o2_status`. adapt had faked the follow-up by seeding `initial_state` with an already-`Cancelled` O2 and asking one question; the notebook's cell 35 runs on the *same chat* as cell 33, so this is now a genuine two-segment case: cancel, then ask, with `turns_at_most 4` |

Three cases written over the same data: `parallel_order_and_customer_lookup` (two independent
lookups that belong in one turn), `cancel_unknown_order` (the `False` branch of `cancel_order`),
`order_o1_details` (single-lookup read-only counterweight).

Every case carries `sim.oracle_plan`, `sim.critical_tool: "cancel_order"` and an explicit
`sim.retrieval_tools: []`.
