# ATTRIBUTION — anthropics/claude-quickstarts `agents/` as an upshift agent directory

## Upstream

- Repository: <https://github.com/anthropics/claude-quickstarts> (17.6k stars), directory `agents/`
- Commit extracted from: `3313e9716fb5b977248bcd06cb0cc86a8c547b9b`
- License: MIT, Copyright (c) 2023 Anthropic (`LICENSE` at the repo root). The prompt text and
  tool schemas below are reproduced from that MIT-licensed source.

The `agents/` quickstart is a plain Anthropic Messages agent: one system prompt, a list of
`{name, description, input_schema}` tools, and a tool-calling loop over
`client.messages.create` (`agent.py:117`). That is exactly upshift's `messages` endpoint, so it
maps onto the five-file contract with no framework shim.

**Why this target:** its loop executes *every* `tool_use` block of a turn concurrently —
`asyncio.gather` over the whole block list, `utils/tool_util.py:27-35` — so the design assumes
several tool calls per assistant turn. That makes it the natural probe for the documented
Fable 5 → 5.1 change where a model that batched tool calls starts issuing them one per turn
(DESIGN.md, `serialized_tool_calls`).

### The schemas were generated by running upstream's code, not transcribed

`tools.json` is the output of importing upstream's tool classes and calling their own
`to_dict()`, plus `asyncio.run(mcp.list_tools())` for the MCP calculator — the same objects the
agent sends on the wire. Two consequences worth naming, because both differ from a
hand-transcription (and from what `upshift adapt` produced):

- `file_read` / `file_write` descriptions keep the **leading newline and 12-space indentation**
  of upstream's triple-quoted strings. `Tool.to_dict()` does not dedent, so that whitespace is
  what Claude actually receives.
- `calculator`'s schema is FastMCP's generated one: the description is the **whole docstring**
  (including the `Args:`/`Returns:` sections and the "Only these exact symbols are supported,
  not words" note), and the parameter schema carries pydantic's `title` keys plus
  `"title": "calculatorArguments"` and no per-argument descriptions.

**Verified upstream fact (blocking, unrelated to the migration):** at `3313e97`,
`import agents.agent` — the import the notebook itself performs — fails with
`ImportError: cannot import name 'MCPConnection' from partially initialized module
'agents.utils.connections'`. `utils/connections.py:11` imports `tools/mcp_tool.py`, which
imports back from `utils.connections` at line 5, and `agents/__init__.py:3` pulls that chain in
on any import of the package. The two plain-Python tool modules were therefore loaded under a
synthetic package supplying only `.base`, and `calculator_mcp.py` was loaded directly. Nothing
about the extracted schemas depends on that workaround; it is recorded because it is a real
defect in the upstream directory.

Derivation environment: Python 3.12, `mcp==1.9.0` (upstream pins no version; `agents/README.md:48`
only says "`mcp` Python library". `mcp>=2` moves `FastMCP` out of `mcp.server`, so
`calculator_mcp.py` does not import at all on it).

## What was dropped, and why

- **The web-search line of the system prompt.** The notebook's agent has a Brave Search MCP
  server; a deterministic eval suite cannot have one (network, live results). The prompt is
  reproduced byte for byte from cell 5 with the single line
  `1. Web search (brave_web_search, brave_local_search)` deleted and **nothing else changed** —
  including the numbering, which therefore starts at `2.`, and the trailing space after
  `(calculate)`. Renumbering would have been a second edit to text we are otherwise reproducing
  verbatim; the file is what upstream wrote minus one line, and this paragraph is the record.
- The prompt names the calculator `calculate` while the tool is actually named `calculator`
  (`calculator_mcp.py:12`, `@mcp.tool(name="calculator")`). That mismatch is upstream's, at this
  commit, and is reproduced rather than fixed.
- `tools/web_search.py` and `tools/code_execution.py` (Anthropic server tools, notebook cell 10)
  are not included: both require the live API to execute.
- The prompt does not mention `file_read` / `file_write`. Upstream's `Agent` has **no** canonical
  tool list — `tools` is a constructor argument (`agent.py:40`) and MCP tools are added at
  runtime — so the tool list here is ours: the four bundled tools that are pure Python or
  deterministic arithmetic. The prompt stays the notebook's.

## Deltas from the real runtime

- **`temperature` is not sent.** Upstream always sends `temperature: 1.0` (`agent.py:89`,
  default at `agent.py:29`). Both Fables reject non-default sampling parameters with a 400
  (DESIGN.md, `api_error_unsupported_sampling_params`) — on **both** the baseline and the
  candidate, so it is a pre-existing incompatibility of the upstream config, not the 5 → 5.1
  migration this suite measures. Sending it would make every case fail on both models and
  measure nothing. It is dropped, and named here instead.
- **No `extra_headers`.** Upstream merges `{"anthropic-beta": "code-execution-2025-05-22"}`
  into every request (`agent.py:109-119`). upshift sends no beta header; the code-execution
  server tool is not part of this agent, so the header would advertise a capability the agent
  does not have.
- **Turn cap.** Upstream's loop is `while True` (`agent.py:104`) with no bound. `agent.json`
  sets `max_turns: 12`.
- **No history truncation.** Upstream calls `self.history.truncate()` each iteration
  (`agent.py:105`, a 180k-token context window at `agent.py:30`); upshift's loop is
  append-only. No case here comes near that window.
- **Tool-result shape.** Upstream puts `str(result)` in the `tool_result` block
  (`utils/tool_util.py:16`); upshift JSON-encodes whatever `Backend.execute` returns, so
  upstream's bare string arrives as `{"output": "..."}`. Upstream's own error *strings* (e.g.
  `"Error: File not found at data/x.txt"`) stay inside `output`, exactly as upstream sends them.
  Only failures upstream would raise on — unknown tool, non-object arguments, a missing
  required argument (a `TypeError` caught at `utils/tool_util.py:20-22` and returned with
  `is_error`) — become `{"error": ...}`, which the loop marks `is_error` too.
- **Filesystem → per-case fixture tree.** `FileReadTool` / `FileWriteTool` touch the real
  filesystem. `backend.py` reimplements them over the `{"files": {...}}` map in each case's
  `initial_state`: same operation dispatch, same `max_lines` truncation, same `📄`/`📁` listing
  format, same reply and error sentences (they are quoted in `backend.py`'s module docstring
  against the upstream line numbers). No Docker, no temp directories, no clock.
- **`state()` adds a write log.** `writes` / `write_count` have no upstream counterpart; they
  exist so a case can assert "the model changed nothing" without guessing at file bytes.
- **No streaming, no MCP transport.** `calculator` runs in-process rather than over stdio, and
  `think` returns upstream's constant `"Thinking complete!"` (`think.py:32`).
- **Model.** `agent.json` names `claude-fable-5`; upstream's `ModelConfig` default is
  `claude-sonnet-4-20250514` (`agent.py:27`) and the notebook's cell 5 agent passes
  `claude-3-7-sonnet-20250219`. The model is the variable under test, so it is set by the
  experiment, not by upstream.

## The eval cases are ours

`agents/` ships no eval suite. `cases/cases.json` is upshift's: two smoke cases whose questions
come from upstream's own tests (`test_message_params.py:65` "What is 2+2?" and
`test_message_params.py:126` "What is 10/2?"), one from the README's usage example
(`README.md:24-38`, an `Agent` with `ThinkTool` asked "What should I consider when buying a new
laptop?"), and five written for
this target — four asserting the batching contract (`turns_at_most`) that
`utils/tool_util.py`'s parallel executor exists to serve, and one asserting the agent does not
write to a tree it was only asked to read.

The `sim.oracle_plan` blocks are also ours. They are a replay script for `--provider sim`, not
evidence: their final messages contain the answers the case checks for, so a sim baseline
satisfies `response_contains` by construction. Per DESIGN.md, sim runs validate the machinery
and never the thesis; only `--provider anthropic` runs are evidence about a model.

## Reproducing

```shell
uv run pytest -q tests/test_agents_claude_b.py
uv run upshift upgrade --agent agents/quickstart-agent --provider sim \
    --baseline-model sim-fable-5 --candidate-model sim-fable-5-1 --tag qs-sim
```
